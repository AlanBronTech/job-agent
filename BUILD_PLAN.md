# Build plan

Eight phases, one dropped. Each is one Claude Code session, each ends with
something that runs. Do not start a phase before the previous one's exit
criterion is met.

Timebox: **two weeks to first real application generated by the tool.** If it
slips past that, cut scope — Phase 5 goes first, then Phase 8.

Scope decisions taken 2026-09-01, after Phase 3 was working:

* **Documents are written to a local folder, not Google Drive.** Uploading is
  a manual step Alan takes when it suits him. This removes the OAuth setup
  from the critical path entirely. Drive upload is in "Later" below, to be
  added only if the manual step turns out to annoy him.
* **Phase 6 (Gmail auto-triage) is dropped.** Alan reviews job alerts himself
  every couple of days and prints the ones worth a look. That is the same
  triage with better judgment and no OAuth, no polling, no launchd.
* **A local UI is added as Phase 8**, after the eval harness. See it for why
  it comes last rather than first.

---

## Phase 0 — Profile as data (do this yourself, not with Claude Code)

The scaffolded `profile/*.yaml` files are drafts built from prior conversations.
They contain errors and gaps. Fix them by hand before writing any code. Every
downstream output is only as good as this.

Checklist:
- [ ] Every role has correct dates, company, title
- [ ] Every *achievement* bullet has a number in it or is deleted. Bullets
      that state a fact rather than claim an achievement (a certification, an
      equity position, a sale) are exempt — a number would be noise.
- [ ] Every bullet is tagged with at least one theme
- [ ] Story bank has situation/action/result written out in full, in your voice
- [ ] `voice.md` has 2 real cover letters you were happy with, pasted in full

**Exit criterion:** you'd be comfortable if an interviewer read the YAML.

## Phase 1 — Skeleton, config, profile loader

Prompt:

> Read CLAUDE.md. Set up the project skeleton: pyproject.toml with uv, the
> package layout described in CLAUDE.md, a config module reading from .env
> (ANTHROPIC_API_KEY, ANTHROPIC_MODEL, DRIVE_RESUME_FOLDER_ID,
> DRIVE_COVERLETTER_FOLDER_ID, DB_PATH), and `core/profile.py` which loads and
> validates profile/*.yaml into pydantic models. Add `jobagent profile validate`
> as the first CLI command — it should print a summary and fail loudly on
> schema errors. Write unit tests for the loader including malformed input.

**Exit:** `uv run jobagent profile validate` prints your role and story counts.

## Phase 2 — JD ingestion and parsing

Prompt:

> Implement JD ingestion. `jobagent jd add` accepts --file, --stdin, or opens
> $EDITOR for paste. It calls the LLM via adapters/llm.py using
> prompts/parse_jd.md to produce a structured JobDescription (pydantic):
> title, company, location, work_type, salary_range, seniority, must_haves[],
> nice_to_haves[], tech_stack[], responsibilities[], red_flags[], source,
> raw_text, ingested_at. Persist to SQLite via core/store.py. Add
> `jobagent jd list` and `jobagent jd show <id>`. Mock the LLM in tests; add
> three real JD fixtures.

**Exit:** you can paste a Seek JD and get a clean structured record back.

## Phase 3 — Fit scoring and go/no-go

The highest-value phase. This is the one that saves you days.

Prompt:

> Implement core/scoring.py. Given a JobDescription and the Profile, produce a
> FitAssessment: overall_score 0-100, per-requirement match (met / partial /
> gap) with the evidence bullet from the profile that supports it,
> gap_list with severity, verdict (apply / apply_with_caveats / skip) with a
> one-paragraph blunt rationale, emphasise[] (what to lead with),
> challenge_points[] (what a recruiter or interviewer will push back on), and
> suggested_talking_points[]. Use prompts/score_fit.md. The prompt must forbid
> claiming any capability not evidenced in the profile. Add `jobagent score
> <jd_id>` with rich formatted output.

**Exit:** run it against the Toshiba JD. If it doesn't surface the tech-stack
mismatch as a challenge point, the prompt is wrong — iterate until it does.

## Phase 4 — Document generation (local files)

Prompt:

> Implement adapters/docx_writer.py rendering to the format in CLAUDE.md, and
> core/generate.py producing: (a) a tailored resume that selects and reorders
> bullets from the profile based on the FitAssessment, never inventing content;
> (b) a cover letter following profile/voice.md; (c) answers to free-text
> application questions supplied via --questions. Write the .docx files into a
> per-application folder under OUTPUT_DIR, named
> `AlanBron_Resume_<Company>_<YYYYMM>.docx` and
> `AlanBron_CoverLetter_<Company>_<YYYYMM>.docx`. Add `jobagent generate
> <jd_id> --resume --cover --answers`. Include a validation step that flags any
> factual claim in the output not traceable to profile/, and any banned phrase
> from voice.md.

Output layout — one folder per application, so the whole thing can be dragged
into Drive, attached to an email, or zipped without picking files apart:

```
$OUTPUT_DIR/2026-09_Toshiba_EngineeringManager/
    AlanBron_Resume_Toshiba_202609.docx
    AlanBron_CoverLetter_Toshiba_202609.docx
    answers.md          # if --answers was used
    assessment.md       # the FitAssessment that shaped it, for the record
    job-ad.md           # the ad itself, as the parser read it
```

`assessment.md` is there so that months later it is possible to see *why* a
resume was cut the way it was — and so the eval harness has the pairing.
`job-ad.md` is written from the stored `raw_text` rather than copied from the
saved PDF: nothing records where that PDF was and it may since have moved, and
`raw_text` is the text the parser and scorer actually read.

**Exit:** a generated resume and cover letter land in the output folder and
need less than ten minutes of editing.

## Phase 5 — Pipeline tracking

Prompt:

> Extend core/store.py with an applications table: jd_id, status enum
> (identified, applied, recruiter_contact, screening, interview_1,
> interview_2, offer, rejected, withdrawn, ghosted), applied_date, recruiter
> name/agency/contact, next_action, next_action_date, notes, outcome. Add
> `jobagent apply <jd_id>`, `jobagent status`, `jobagent update <id>`,
> `jobagent followup` (shows overdue actions), and `jobagent report
> --fortnight` producing the Workforce Australia activity summary.

**Exit:** `jobagent report --fortnight` gives you the reporting list without
you reconstructing it from memory.

## Phase 6 — Gmail auto-triage — **DROPPED 2026-09-01**

Was: OAuth into Gmail, poll job-alert emails twice a day, score each lead with
a cheap triage prompt, produce a shortlist.

Dropped because the manual version is better. Alan reads the alert emails
himself every couple of days, and deciding which ones are worth a second look
is the one part of this he is faster and more accurate at than a triage prompt
would be. What the tool is for begins at the point where an ad is worth real
attention: he prints it to PDF and runs `jd add`. Building this would have
bought a shortlist he can already produce, in exchange for an OAuth flow, a
token cache, a polling schedule and a launchd plist to maintain.

Reconsider only if the volume of alerts becomes the bottleneck. It is not.

## Phase 7 — Eval harness and interview prep

Prompt:

> Build evals/: a set of past JDs with recorded real outcomes in
> evals/cases.yaml. Run the fit scorer over them and report correlation between
> predicted score and actual outcome, plus per-case diffs. Add a prompt-
> regression mode that reruns after prompt edits and shows what changed. Then
> implement core/prep.py: given a jd_id plus optional interviewer names and
> roles, generate likely questions mapped to specific stories from the story
> bank, with the challenge_points from the FitAssessment as the hard questions.

**Exit:** you can say in an interview "I measured it against fifteen real
applications and here's what the scorer got wrong" — which is the difference
between this and every other LLM wrapper on a resume.

## Phase 8 — Local UI

Prompt:

> Add a FastAPI app served on localhost with HTMX templates, calling the same
> `core/` services the CLI calls and adding no business logic of its own. Screens:
> a job list with verdict and score, one job detail view showing the assessment
> (constraints, requirements, challenge points, questions to ask), a drop zone
> that runs the PDF through `jd add`, a button to score, a button to generate,
> and the pipeline status board from Phase 5. Add `jobagent ui`, which starts
> the server and opens a browser.

**Why last, not first.** `core/` has been written from the start to be callable
from a web handler — no printing, no typer, no sys.exit — so this is genuinely
additive whenever it happens. But the shape of what a screen would display has
changed twice in a single day of building the scorer, and screens are the most
expensive thing to rework. The CLI is the cheap place to find out what the
workflow actually is.

**A local web page rather than a native app**, despite the preference for an
app, because a native macOS app means a second language and toolchain, its own
packaging and signing, and a UI layer that cannot reuse a line of the Python.
A localhost page in the browser gets the same "click things instead of typing
commands" benefit for a fraction of the work, and `jobagent ui` opening a
browser window is close enough to double-clicking an app that the difference is
mostly the dock icon. If it later earns a real app, the FastAPI service is the
back end that app would have needed anyway.

**Exit:** the daily loop — see the shortlist, read an assessment, generate
documents — happens without typing a command.

## Later (only if the tool is actually earning its keep)

- **Google Drive upload.** Deferred 2026-09-01: documents are written locally
  and uploaded by hand when convenient. `adapters/drive.py` uploading a
  finished application folder into a configured Drive folder is a contained
  addition if the manual step becomes an irritation.
- **Prompt caching for the scorer.** Every `score` call re-sends the whole
  ~26k-token profile, at $0.16-$0.21 and up to nine minutes per ad. Phase 7
  runs the scorer repeatedly over the eval set and will feel it.
- Multi-user support and a hosted version (this is the fractional-consulting
  product, if there is one)
